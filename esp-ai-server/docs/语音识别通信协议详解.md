# 语音识别（ASR）通信协议详解

本文档详细描述 ESP-AI 设备端与服务器之间在语音识别全流程中的通信协议，包括消息时序、数据格式、状态转换和异常处理。

---

## 一、整体架构

协议分为客户端（ESP 设备端）和服务端（云端 AI 服务）两端，基于 WebSocket 双向消息通信，覆盖连接鉴权、会话生命周期管理、语音 ASR 采集、TTS 语音合成播放、保活心跳、会话打断等全语音对话流程。

消息流向约定：
- **蓝色箭头** `→`：客户端 → 服务端（上行消息）
- **红色箭头** `←`：服务端 → 客户端（下行消息）

---

## 二、分阶段完整消息时序表

### 阶段 1：WebSocket 连接与鉴权阶段

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 客户端 → 服务端 | 连接服务 | WebSocket 握手请求，携带 URL 参数 | 客户端主动发起 WebSocket 服务连接 |
| 服务端 → 客户端 | `error` | 错误信息 | 服务端鉴权失败，连接失败 |
| 服务端 → 客户端 | `play_audio_ws_conntceed` | 纯文本字符串 | 服务端鉴权成功，通知客户端连接建立完成 |

**连接参数示例**：
```
ws://192.168.31.176:8088/?v=2.95.51&device_id=D8:3B:DA:6D:D9:3C
&api_key=&ext1=0f7ef924cbd246569c37f4dcb05603e6&ext4=http
&ext5=192.168.31.176&ext6=8088&ext7=asrpro&bitrate=128
&AUDIO_BUFFER_SIZE=10240
```

### 阶段 2：网络时延测试阶段

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 客户端 → 服务端 | `play_audio_ws_conntceed` | `{"type": "play_audio_ws_conntceed"}` | 客户端通知服务端已准备好接收音频 |
| 服务端 → 客户端 | `stc_time` | `{"type": "stc_time", "stc_time": "1234567890"}` | 服务端下发探测起始时间戳 |
| 客户端 → 服务端 | `cts_time` | `{"type": "cts_time", "stc_time": "1234567890"}` | 客户端上报回传时间，服务端完成往返时延计算 |

### 阶段 3：会话 ID 初始化与提示音下发阶段

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 服务端 → 客户端 | 二进制音频帧 | `session_id: 0001` + `status: 00` + 音频数据长度(6字节) + 音频裸数据 | 下发服务连接成功提示音 |
| 客户端 → 服务端 | `client_out_audio_over` | `{"type": "client_out_audio_over", "session_id": "0001", "session_status": "03", "tts_task_id": ""}` | 客户端提示音播放完成上报 |

**音频数据帧格式**：
```
+------------+------------+----------------+------------+
| 会话ID(4B) | 状态(2B)   | 音频长度(6B)   | 音频数据   |
+------------+------------+----------------+------------+
|   0001     |    00      |   002048       |  [二进制]  |
+------------+------------+----------------+------------+
```

**会话 ID 定义**：
| ID 值 | 描述 |
|-------|------|
| `0000` | 零值，无有效会话数据 |
| `0001` | 服务连接成功提示 |
| `0010` | TTS 待播放音频（含唤醒提示音） |
| `1002` | 休息时间回复数据 |

**会话状态定义**：
| ID 值 | 描述 |
|-------|------|
| `00` | 普通音频片段 |
| `01` | TTS 片段（分包数据最后一个片段） |
| `02` | 单个对话的 TTS 最后一组数据，无需接续分片 |
| `03` | 单个对话的 TTS 最后一包数据，无需继续对话 |

---

### 阶段 4：对话会话启动阶段

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 客户端 → 服务端 | `start` | `{"type": "start"}` | 客户端唤醒对话，主动发起新一轮 AI 对话会话 |
| 服务端 → 客户端 | `session_start` | `{"type": "session_start", "session_id": "0001"}` | 服务端回复，下发会话开始指令 |
| 服务端 → 客户端 | `instruct` | `{"type": "instruct", "command_id": "on_iat_cb", "data": ""}` | 通知客户端清空显示 |
| 服务端 → 客户端 | `play_audio` | `{"type": "play_audio", "tts_task_id": "0010"}` | 唤醒提示音播放开始 |
| 服务端 → 客户端 | `session_status` | `{"type": "session_status", "status": "tts_chunk_start"}` | 唤醒提示音数据开始下发 |
| 服务端 → 客户端 | 二进制音频流 | `session_id(0010) + status(00) + 音频数据` | 唤醒提示音分片（如 du.mp3） |
| 服务端 → 客户端 | 二进制结束帧 | `session_id(0010) + status(03)` | 唤醒提示音结束 |
| 服务端 → 客户端 | `session_status` | `{"type": "session_status", "status": "tts_real_end"}` | 唤醒提示音全部发送完毕 |
| 客户端 → 服务端 | `client_out_audio_over` | 音频播放完成上报 | 设备确认唤醒提示音播放完成 |
| 服务端 → 客户端 | `session_status` | `{"type": "session_status", "status": "iat_start"}` | 服务端通知客户端开始录音 |

**说明**：
- 服务端收到 `start` 后，先播放唤醒提示音（如 `du.mp3`），等待设备播完
- 唤醒音频使用与 TTS 相同的 session_id (`0010`)，确保设备能正确解码播放
- 设备播完唤醒音后回复 `client_out_audio_over`，服务端才发送 `iat_start`
- 客户端收到 `iat_start` 后，屏幕显示"聆听中"，开始采集麦克风音频

---

### 阶段 5：麦克风音频流（ASR 语音采集）阶段

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 客户端 → 服务端 | `client_available_audio` | `{"type": "client_available_audio", "session_id": "0001", "value": "2024"}` | 客户端上报本地音频缓存区剩余大小，用于流量控制 |
| 客户端 → 服务端 | 二进制音频流 | 512 字节 PCM 原始音频数据 | 客户端上行麦克风音频流 |
| 客户端 → 服务端 | `iat_end` | `{"type": "iat_end"}` | 客户端 VAD 人声检测结束，主动停止 ASR 语音识别（可选） |
| 客户端 → 服务端 | `session_status` | `{"type": "session_status", "status": "iat_end"}` | 客户端上报停止录音 |
| 服务端 | ASR 停止 | 内部逻辑 | 云端语音识别服务终止 |

**音频数据规范**：
- **格式**：512 字节标准 PCM 原始音频流
- **传输特性**：流式分片传输，时间间隔和单次大小均为动态自适应

**说明**：
- 客户端持续发送音频数据，直到以下情况之一发生：
  1. 用户说完话，客户端 VAD 检测结束，发送 `iat_end`
  2. 服务端检测到 5 秒无音频，主动结束会话
  3. 服务端 ASR 识别到 VAD 结束（slice_type=2）

---

### 阶段 6：TTS 语音合成 & 音频播放阶段

ASR 识别完成后，服务端下发 AI 回复的合成语音，客户端完成播放。

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 服务端 → 客户端 | `session_status` | `{"type": "session_status", "status": "iat_end"}` | 服务端下发录音结束状态 |
| 服务端 → 客户端 | `iat` | `{"type": "iat", "text": "识别到的文本"}` | 服务端下发 ASR 识别结果 |
| 服务端 → 客户端 | `llm` | `{"type": "llm", "text": "AI 回复内容"}` | 服务端下发 LLM 回复文本 |
| 服务端 → 客户端 | `play_audio` | `{"type": "play_audio", "tts_task_id": "0010"}` | 服务端下发音频播放开始事件 |
| 服务端 → 客户端 | `session_status` | `{"type": "session_status", "status": "tts_chunk_start"}` | 服务端下发当前 TTS 音频段正式开始 |
| 服务端 → 客户端 | 二进制音频流 | `session_id(0010) + status(00) + 长度(6B) + 音频数据` | 服务端分段下发 TTS 合成后的二进制语音数据流 |
| 服务端 → 客户端 | 二进制结束帧 | `session_id(0010) + status(03)` | 单个对话的 TTS 最后一包数据 |
| 服务端 → 客户端 | `session_status` | `{"type": "session_status", "status": "tts_chunk_end"}` | 服务端下发当前 TTS 音频段全部传输结束 |
| 客户端 → 服务端 | `client_available_audio` | `{"type": "client_available_audio", "value": "0"}` | 流量控制上报 |
| 客户端 → 服务端 | `client_out_audio_over` | `{"type": "client_out_audio_over", ...}` | 客户端音频播放完成上报 |

**TTS 响应完整流程**：
```
1. {"type": "session_status", "status": "iat_end"}
2. {"type": "iat", "text": "用户说的话"}
3. {"type": "llm", "text": "AI 的回复"}
4. {"type": "play_audio", "tts_task_id": "0010"}
5. {"type": "session_status", "status": "tts_chunk_start"}
6. [二进制音频帧 1]
7. [二进制音频帧 2]
8. ...
9. [二进制结束帧: session_id + "03"]
10. {"type": "session_status", "status": "tts_chunk_end"}
```

---

### 阶段 7：会话结束 / 待机阶段

当用户 5 秒未说话，或对话自然结束时，进入待机状态。

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 服务端 → 客户端 | `session_status` | `{"type": "session_status", "status": "session_end"}` | 服务端通知客户端进入休息状态（更新屏幕） |
| 服务端 → 客户端 | `session_end` | 纯文本字符串 `"session_end"` | 服务端通知客户端停止录音和音频发送 |

**说明**：
- 服务端需要**先后发送两条消息**：
  1. JSON `session_status: session_end` → 客户端屏幕切换到"休息中"
  2. 纯文本 `session_end` → 客户端停止录音和发送音频数据
- 这两条消息缺一不可，否则会出现屏幕状态已切换但设备仍在发送音频的问题

---

### 阶段 8：会话打断 / 停止全流程

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 客户端 → 服务端 | `session_stop` | `{"type": "session_stop", "session_id": "0001"}` | 客户端主动请求停止一切音频活动、打断当前对话 |
| 服务端 → 客户端 | `session_stop_ack` | `{"type": "session_stop_ack", "session_id": "0001"}` | 服务端应答会话已成功停止 |

---

### 阶段 9：长连接保活心跳机制

| 消息流向 | 消息名称 | 消息内容 / 携带参数 | 业务含义 |
|---------|---------|-------------------|---------|
| 服务端 → 客户端 | `ping` | `{"type": "ping"}` | 服务端主动发送心跳探测包 |
| 客户端 → 服务端 | `pong` | `{"type": "pong"}` | 客户端心跳应答回复包 |

**协议约定**：心跳发送间隔 500ms 一次

## 四、客户端全状态总览

| 状态 | 触发条件 | 屏幕显示 |
|------|---------|---------|
| 初始状态 | 设备上电 | "休息中" |
| 连接中 | WebSocket 连接建立 | "网络连接中" |
| 聆听中 | 收到 `iat_start` | "聆听中" |
| 说话中 | 收到 `iat_end` 或 TTS 开始 | "说话中" |
| 休息中 | 收到 `session_end` | "休息中" |

**状态转换流程**：
```
休息中 --(唤醒/start)--> 播放唤醒音 --(client_out_audio_over)--> 聆听中 --(iat_end/VAD结束)--> 说话中 --(TTS结束/session_end)--> 休息中
```

## 五、服务端全状态总览

| 阶段 | 服务端行为 |
|------|-----------|
| 连接建立 | 接收客户端连接，发送 `play_audio_ws_conntceed` |
| 时延测试 | 下发 `stc_time`，接收 `cts_time` |
| 提示音下发 | 发送连接成功提示音（session_id: 0001） |
| 会话开始 | 收到 `start`，发送 `session_start` + `iat_start` |
| ASR 识别 | 接收音频流，发送到腾讯云 ASR 服务 |
| TTS 合成 | ASR 结束后，调用 LLM 生成回复，合成 TTS 音频 |
| TTS 下发 | 分段发送 TTS 音频帧 |
| 会话结束 | ASR 启动后 N 秒无识别结果，或对话结束。发送 `session_status: session_end` + `session_end` |
| 心跳保活 | 每 500ms 发送 `ping`，接收 `pong` |

## 七、异常处理

### 7.1 无音频超时

**场景**：用户唤醒设备后 5 秒未说话。

**处理流程**：
1. 服务端 `check_no_audio_timeout` 检测到 5 秒无音频数据
2. 设置 `asr_processed = True`
3. 取消 `no_asr_result_timer_task`
4. 发送 `session_status: session_end`（JSON）
5. 发送 `session_end`（纯文本）
6. 设备屏幕切换到"休息中"，停止录音

### 7.2 无 ASR 结果超时

**场景**：用户说话了但 ASR 未识别到有效内容。

**处理流程**：
1. 服务端 `check_no_asr_result_timeout` 检测到 5 秒无 ASR 结果
2. 发送 `session_status: session_end` + `session_end`
3. 或者检测到 2 秒无新 ASR 结果，发送 TTS 响应（空内容）

### 7.3 会话打断

**场景**：用户在中途按下按钮打断当前对话。

**处理流程**：
1. 客户端发送 `session_stop`
2. 服务端停止 ASR 和 TTS
3. 服务端发送 `session_stop_ack`
4. 设备回到待机状态

## 八、数据帧构成规范

### 8.1 指令数据

所有会话控制、心跳、设备状态、硬件上报、配置回调均使用短指令交互，区分上下行。

**文本消息格式**：
```json
{
  "type": "消息类型",
  "其他字段": "值"
}
```

### 8.2 音频数据帧

**设备上报音频流（设备 → 服务端）**：
- 数据格式：512 字节标准 PCM 原始音频流
- 传输特性：流式分片传输

**服务端下发音频帧（服务端 → 设备）**：

帧结构：`会话ID(4字节) + 会话状态(2字节) + 音频数据长度(6字节) + 音频数据`

| 字段名称 | 固定字节长度 | 字段说明 |
|---------|------------|---------|
| 会话 ID | 4 字节 | 唯一标识一次完整语音交互会话 |
| 会话状态 | 2 字节 | 标识当前会话所处业务状态 |
| 音频数据长度 | 6 字节 | 声明后续音频载荷的字节长度，不足补0 |
| 音频数据 | 动态大小 | TTS 语音合成原始音频载荷 |

**示例**：
```
原始数据：0010 + 00 + 002048 + [2048字节音频数据]
编码后：  b'0010' + b'00' + b'002048' + audio_data
```

---

## 九、注意事项

1. **session_end 双消息机制**：服务端必须先后发送 JSON `session_status: session_end` 和纯文本 `session_end`，缺一不可。
2. **心跳方向**：新协议中由服务端主动发送 `ping`，客户端回复 `pong`。
3. **音频缓冲区控制**：客户端通过 `client_available_audio` 上报缓冲区大小，服务端据此控制音频下发速度。
4. **会话 ID 一致性**：TTS 音频帧中的 `session_id` 应与 `play_audio` 消息中的 `tts_task_id` 保持一致。
5. **状态同步**：服务端和设备端的状态转换必须严格同步，避免出现服务端已结束但设备仍在发送音频的情况。
