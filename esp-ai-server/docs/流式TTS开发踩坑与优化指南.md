# 流式 TTS（ASR → LLM → TTS）开发踩坑与优化指南

本文档记录了 ESP-AI 服务端在 ASR 语音识别 → LLM 大模型 → TTS 语音合成全链路流式处理中需要注意的关键事项，以及不注意这些事项会导致的问题。

---

## 一、开发注意事项

### 1. 流控公式方向

**注意**：设备回报的 `client_available_audio` 含义是**设备音频缓冲区剩余空闲空间**（剩余可用字节数），不是已用空间。

| 变量 | 含义 | 值大时 | 值小时 |
|------|------|--------|--------|
| `client_available` | 设备缓冲区剩余空闲空间 | 可以多发 | 少发或暂停 |

**正确做法**：
- `max_send = min(client_available, 10240)`（一次最多发这么多字节）
- `if client_available <= 0` → 缓冲区满，暂停发送

**不注意会导致**：
- 语音卡顿：如果公式写反（例如 `max_send = 10240 - client_available`），空闲大时反而发送少，导致音频传输慢
- 设备无响应：如果缓冲区满判定写反（例如 `if client_available >= 10240`），空闲大时反而暂停发送

### 2. 避免流控死锁

**注意**：音频流控（发送方等待接收方缓冲区空闲）存在**天生死锁风险**：
```
发送方: 等待 available > 0
接收方: 需要收到数据才回传 available
→ 如果初始 available=0，双方互等 → 死锁
```

**正确做法**：
1. TTS 开始时**强制重置** `available = 10240`
2. **首次发送无条件通过**，不检查 `available`
3. 长时间无进展时**强制发送一帧**打破僵局

**不注意会导致**：
- 设备完全没声音：sender 启动后看到 `available=0` 不发任何音频，设备收不到就不会回报，永远死锁

### 3. 第三方服务 WebSocket 必须有心跳

**注意**：火山引擎 TTS、腾讯云 ASR 等第三方服务的 WebSocket 连接都有服务端空闲超时（通常 30 秒）。

**正确做法**：
```python
websockets.connect(url, ping_interval=15, ping_timeout=10)
```

**不注意会导致**：
- 连接断开：当 LLM 流式输出较长时，上一句 TTS 完成到下一句 TTS 发送之间 WebSocket 空闲，会被服务端断开
- 语音中断：连接断开后，后续句子的 TTS 合成失败，导致回复不完整

### 4. 连接复用 vs 每次新建

**注意**：长连接复用带来心跳管理成本。对于流式 TTS（句子之间有间隔），需要权衡：

**正确做法**：
- 加心跳保活 + 断连自动重连（推荐）
- 或者每次合成前新建连接（更简单但增加延迟）

**不注意会导致**：
- 连接不稳定：如果不处理断连，连接断开后整个流程会中断
- 延迟增加：如果每次都新建连接，会增加 TTS 合成的启动延迟

### 5. Drain 模式设计

**注意**：当 LLM 输出完毕、TTS 合成完毕，仅剩音频帧需要发送给设备时，应启用 drain 模式。

**正确做法**：
- **关闭事件等待**：不会再产生新帧，等事件是浪费时间
- **关闭流量控制**：设备不回传时也要强制发送
- **最小化延迟**：5ms 间隔即可，远低于正常模式的 30-150ms

**不注意会导致**：
- 超时被取消：drain 时仍然每轮等待 30-80ms，110 帧需要 3-9 秒，导致 8 秒超时
- 语音播放不完整：drain 超时后被强制取消，剩余音频帧未发送

### 6. 结束帧时机（TCP ACK 确认机制）

**注意**：sender 排空所有音频帧后，不要立即发送结束帧（end_frame），也不要仅靠固定延迟。

**正确做法**：
- 利用 `client_available_audio` 作为 TCP ACK 信号
- 设备每收到一批音频数据，会通过 WebSocket 回报 `client_available_audio`
- 收到此消息 = 之前所有音频帧都已递达设备，此时再发送 end_frame

**不注意会导致**：
- 播放不完整：如果 `end_frame`（6 字节小包）在最后一个大音频帧之前被设备 TCP 栈解析，设备可能关闭 session，导致后续音频帧被丢弃
- 设备永不回报：设备播放了部分音频但从不发送 `client_out_audio_over`，导致服务端一直等待

### 7. 播放完成等待

**注意**：设备播放长音频可能需要数十秒甚至数分钟。

**正确做法**：
- 用 **循环分片等待**（每次 10 秒），而非一次性 `wait_for(..., timeout=120)`
- 每次超时输出进度日志，方便排查设备是否仍在播放
- 超时后**优雅降级**，不要 crash

**不注意会导致**：
- 服务卡死：如果一次性等待 120 秒，期间无法处理其他消息
- 连接断开：如果等待逻辑有问题，可能导致 WebSocket 连接异常

### 8. 协议一致性

**注意**：`play_audio` 的 `tts_task_id`、TTS 二进制音频帧的 `session_id`、TTS 结束帧的 `session_id` 必须使用**同一个值**。

**正确做法**：
- 统一使用 TTS 专用 session_id: `"0010"`
- 连接成功提示音使用 `"0001"`（仅初始连接时用）
- 唤醒提示音也使用 `"0010"`（与 TTS 共用，设备只识别此 ID）

**不注意会导致**：
- 设备没声音：设备无法匹配音频数据和播放指令
- 播放混乱：session_id 不一致可能导致设备播放错误的音频

### 9. 数据结构选择

**注意**：不同数据结构在队列场景下性能差异很大。

**正确做法**：
- 使用 `deque` 做队列：`frames.popleft()` O(1) 弹出
- 避免使用 `list` 做队列：`frames.pop(0)` O(n) 元素搬移

**不注意会导致**：
- 内存浪费：`list.copy()` 每轮完整拷贝，内存占用高
- 性能下降：`list.pop(0)` 时间复杂度 O(n)，处理大量帧时速度慢

### 10. 异步编程最佳实践

**注意**：异步编程中，事件驱动优于轮询。

**正确做法**：
- 使用 `asyncio.Event` 事件驱动：有数据才唤醒
- 避免死循环 `sleep(0.05)` 轮询：CPU 空转

**不注意会导致**：
- CPU 高空转：轮询会占用大量 CPU 资源
- 响应延迟：轮询间隔固定，可能导致数据处理不及时

### 11. 超时设置要匹配实际场景

**注意**：不同环节的超时设置需要根据实际场景调整。

**正确做法**：
- ASR 接收超时：30 秒（腾讯云 ASR 有返回间隔）
- TTS 合成超时：单句通常 1-3 秒，长句可能需要更长
- sender 排空超时：取决于总音频量和网络速度，**至少 60 秒**
- 设备播放超时：取决于音频时长，**建议 120 秒**

**不注意会导致**：
- 流程中断：超时设置过短，导致正常处理被强制终止
- 资源占用：超时设置过长，可能导致资源长时间被占用

### 12. 重试只针对连接异常

**注意**：重试机制应该只针对连接异常，避免对业务错误重试。

**正确做法**：
- 对 `ConnectionClosed`、`TimeoutError`、`OSError` 等连接异常重试
- 对 `SessionFailed`、`Error` 等业务错误不重试

**不注意会导致**：
- 死循环：对业务错误重试，可能导致无限循环
- 资源浪费：无效重试会占用网络和服务器资源

## 二、问题 → 根因 → 后果速查表

| 现象 | 根因 | 后果 |
|------|------|------|
| 火山引擎 WS 连接超时 | `ping_interval=None` 禁用心跳 | 连接断开，TTS 合成失败，语音中断 |
| 连接断了不恢复 | 无重连逻辑 | 后续句子的 TTS 合成失败，回复不完整 |
| 设备没声音（一） | `tts_task_id` 与音频帧 `session_id` 不一致 | 设备无法匹配音频数据，完全没声音 |
| 设备没声音（二） | `available=0` 时 sender 不发 → 死锁 | 设备收不到音频，永远不回报，死锁 |
| 语音卡顿 | 流控公式写反 | 空闲大时反而发送少，音频传输慢，卡顿 |
| drain 超时被取消 | drain 模式仍 sleep 30ms + 超时仅 8s | 剩余音频帧未发送，播放不完整 |
| CPU 高空转 | 轮询 `sleep(0.05)` 检查帧队列 | 服务器 CPU 占用高，影响其他服务 |
| 帧拷贝内存浪费 | `list.copy()` 每轮完整拷贝 | 内存占用高，可能导致 OOM |
| 长回答播完不回报 | end_frame 与音频帧 TCP 乱序 | 设备 session 提前关闭，后续音频被丢弃 |
| 播放完成等待卡死 | 一次性等待 120 秒 | 服务无法处理其他消息，响应缓慢 |

## 三、最佳实践总结

1. **流控正确**：理解 `client_available_audio` 含义，使用正确的流控公式
2. **死锁防护**：首次强制发送 + 重置缓冲初始值 + 强制发送兜底
3. **心跳保活**：第三方 WebSocket 必须设置心跳
4. **连接管理**：实现断连自动重连，只对连接异常重试
5. **Drain 模式**：关闭事件等待 + 关闭流控 + 最小延迟
6. **TCP ACK**：等设备 `client_available_audio` 确认后再发 end_frame
7. **协议一致**：统一使用 `session_id="0010"` 处理 TTS
8. **数据结构**：使用 `deque` 做队列，`asyncio.Event` 事件驱动
9. **超时合理**：根据实际场景设置合适的超时时间
10. **优雅降级**：遇到异常时优雅处理，避免 crash
